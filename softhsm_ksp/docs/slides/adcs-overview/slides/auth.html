The token decides how it is authenticated, not the provider

The provider reads CK_TOKEN_INFO.flags for the scope's slot and honours all three models PKCS#11 describes. Until recently it demanded a PIN of every token — so a hardware HSM with a PIN pad, the case this project targets, was rejected outright.

No login required

CKF_LOGIN_REQUIRED clear

No C_Login at all. No credential to store anywhere.

Protected path

PIN pad on the device

C_Login with pPin = NULL, per v2.40 §11.6. A configured PIN is deliberately not sent, only logged as unused. Ask your HSM vendor for this one.

PIN required

A credential must reach a headless service

certsrv never calls NCryptSetProperty, so the PIN has to be waiting for it. Four sources, in order.

Precedence

KSP_MACHINE_PIN / KSP_USER_PIN → NCRYPT_PIN_PROPERTY → DPAPI blob → SOFTHSM2_PIN

The blob outranks the ambient variable on purpose: a leftover lab variable must not silently downgrade a deployment that was provisioned properly, while appearing to work. And the registry ACL is the protection, not the encryption — machine-scope DPAPI can be unprotected by anything on the host.
