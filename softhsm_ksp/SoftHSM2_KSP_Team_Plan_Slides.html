Inherit this honestly: what is proven and what is merely written

Read the second column as the real backlog. The provider has never been compiled for Windows, so everything that depends on ncrypt.dll is a hypothesis about the code and about the suite that would test it.

Proven by execution

  • 2 051 unit assertions, 27 suites, 86.2 % lines at 100 % functions
  • The real sources against two independent live tokens, each suite run twice
  • RSA and ECDSA signing, key reopen by name, certificate storage, deletion
  • 32 threads over the 16-session pool, compared by signature bytes, under ThreadSanitizer
  • Per-scope token isolation, verified with two tokens and two PINs
  • Five static checks and a mingw cross-compile on every commit

Written, never executed

  • The DLL itself. One of ten source files cannot compile without the CPDK header
  • 40 integration tests and ~150 HLK-conformant checks
  • register_ksp.ps1 — parses and its C# compiles; never run
  • set_ksp_pin.ps1 and the DPAPI registry read behind it
  • Every statement about how ADCS calls a provider on renewal
  • Whether Windows loads an unsigned user-mode KSP at all

Not an engineering question

  • A CA key cannot carry a Windows DACL — PKCS#11 has no ACL model. The token boundary is the whole control
  • Which HSM. If it ships its own KSP, this project may be the wrong tool
  • An OV or EV code-signing certificate, bought by a verified legal entity
  • FIPS posture, which needs certified hardware rather than code

Feature matrix: 103 capability rows, 73 covered · of the 30 open, 10 could start today and 20 are blocked outside the repository · 2 / 10

Spend the most time on the middle column. The temptation on joining will be to read the proven column and conclude the project is nearly done; it is roughly half done, and the unexecuted half is the half that decides whether it works. Five defects have already survived the mock and been caught the first time a real token ran — expect the same ratio when Windows enters the picture.

4 / 10

Week one

Four things to start before anyone writes a line of code

1 · Find the header, and decide the fallback

It is associated with the Cryptographic Provider Development Kit, but that is unconfirmed and two guesses at its location were already wrong. Give someone an MSDN or partner account and a week. Decide now what happens if it cannot be had — reconstructing the function table from observed behaviour is possible and is the riskiest thing anyone could do to this project.

2 · Open the certificate purchase

An OV or EV code-signing certificate needs a verified legal entity, which is weeks of paperwork, not an afternoon. Signing, timestamping and verification are already scripted and CI signs automatically once the secret exists — so the only missing part is the one that cannot be hurried.

3 · Run p11_qualify against the real HSM

One C file, one header, no Windows and no KSP build. It runs all 18 Tier 1 requirements and four strictness probes, and reports which of the three PKCS#11 authentication models the token uses. If the token has a PIN pad, Phase C closes with no work at all.

4 · Get the DACL question answered

Put it to whoever owns the CA's threat model, in writing: is a CA key protected only by the token boundary and its credential acceptable here? The CA MMC's private-key permissions dialog will not work, and an operator must not discover that during an incident.

Also in week one, and it costs a morning: A4 is the one Phase A item still open — a regression test that NCRYPT_SILENT_FLAG combined with each padding flag still resolves the right mechanism. The masking is correct today by construction; nothing stops a future equality comparison breaking CA signing silently.

Items 1, 2 and 4 are not engineering work and should not be assigned to engineers · 4 / 10

If only one slide survives this deck, make it this one. None of these four is hard; all four have long tails; and three of them need authority rather than skill. Item 1's fallback decision matters more than it sounds — reconstructing a function table layout from behaviour is exactly the class of guess that cost this project the SHA-224 identifier and a post-quantum blob format.

The free win

Part of the backlog is blocked only by where it was built

This project was written in a sandbox whose network policy blocks Microsoft Learn. Several findings were therefore recorded as open rather than guessed at — the right call, and one a team with a browser and a partner account retires in an afternoon.

Four tracks, and the skill each one actually needs

Tracks 2, 3 and 4 do not wait for the DLL. Track 1 is the only one that does, and it is also the only one that cannot be accelerated by adding people to it.

Track 1 · blocked until the header arrives

Windows and CNG

Build the DLL, confirm the function-table layout against the real header, register it, then run the 40 integration tests and ~150 HLK checks and triage the first execution of either.

Needs: MSVC and CNG provider experience, and an HLK controller plus a separate test client. One engineer, [W__] weeks.

Track 2 · starts immediately

Token and PKCS#11

Qualify the candidate HSM, stand up per-scope machine and user tokens, close A4, and prove the DPAPI credential path once a machine exists.

Needs: Cryptoki fluency and the vendor's library. One engineer, [W__] weeks, mostly before the machine arrives.

Track 3 · prepares now, runs after gate B

PKI and ADCS operations

Write the pilot runbook for E1–E7, provision the throwaway CA, and document plainly that the private-key permissions dialog will not work.

Needs: a PKI operator, not a developer — someone who has renewed a CA certificate before. Part-time, then full-time at the pilot.

Track 4 · starts immediately

Procurement and governance

The code-signing certificate, the Windows machine, the HSM decision, the DACL risk acceptance, and FIPS posture if it is required.

Needs: budget authority and the CA's threat-model owner. Not an engineer, and the lane most likely to be left unassigned.

7 / 10

Four gates, each one a claim somebody can check

A gate is not a milestone with a date on it. It is a sentence that is either true or false, and no phase starts until the one before it is true.

B

The provider loads, enumerates and signs through the real ncrypt.dll

Not "it compiles". Not "certutil lists it". A signature produced by a key on the token, through the public NCrypt API, verified against BCrypt. Until this is true, every statement in the ADCS plan is a projection — including the ones on these slides.

C

190 written tests have executed, and every failure is triaged

Triaged, not necessarily passing — a first run that finds nothing means the run was wrong. Each failure is classified as a provider defect, a test defect or a documented limitation, and the suite's own counts are reconciled with the docs by the existing checker.

E

E1–E7 pass on a throwaway CA, twice, including renewal with a new key

Twice, because a single pass cannot see what the provider leaves behind — that is how the orphaned-certificate defect was found. Then a service restart and a host reboot, since the credential has to be available before any logon.

F

Signed binary, real HSM, DACL risk accepted in writing

Plus FIPS posture if required, which needs certified hardware rather than a code change. This is what "finalized" means — and the test CA from gate E is destroyed, never promoted.

Standing gate throughout: five static checks, both live-token suites and the mingw cross-compile green on every commit · 7 / 10

The gates exist to stop the project reporting progress it has not made, which is a risk here because so much is written and so little has run. Gate C's wording is deliberate: a first execution of 190 never-run tests that comes back clean is evidence the harness is broken, not that the code is perfect. Four consecutive fault injections once ran against a stale binary in this project and looked undetected.

Seven rules, each one paid for

How to work in this codebase without re-learning its lessons

1 · Break it before you believe it

No claim lands without a fault injection that the suite catches. And restore the injection from a copy made beforehand, never from git — that has destroyed uncommitted work three times.

2 · Two tokens, two passes

One token cannot tell a working selection from an ignored one; one pass cannot see what the provider leaves behind. Each shortcut hid a real defect until the second was added.

3 · Never hand-edit the mock

It once invented two constants and mis-valued two more, and every test passed because the tests read the same wrong numbers. A checker now compares it to the real headers, values and typedef widths both.

4 · The function table is assigned by name

Designated initialisers, permanently. Positional initialisation put a key handle where a HANDLE * belonged and returned success to a caller that then waited forever.

5 · A grep for a fix can match the fix's comment

An audit once reported ten files as correct when none was: the pattern matched the sentence describing the include. Verify with the compiler, not with a search.

6 · The five static checks are the contract

Docs, counts, property tables and the registration script are all machine-compared to the code. They exist because a summary sitting next to a fact does not stay true — the most persistent defect here.

7 · Closing a capability row is two edits

Set the row Covered and delete its gap entry, then regenerate. A status change edits the existing row — appending a new ID left one capability with two rows, one of them asserting the opposite of the other, for three sessions.

And one habit to keep

When the authoritative source is out of reach, record the gap; do not fill it from memory. Both times this project guessed at a Microsoft constant, the guess was wrong and passed every test.

Six risks, ranked by what they cost rather than how likely they are

The top two can each stop the project outright, and both are answered by a phone call rather than by engineering. Answer them first.

# Risk If it happens What to do about it now
R1 The CPDK header cannot be obtained Fatal. There is no DLL and no path to one Escalate through a Microsoft partner channel in week one. Decide the fallback position explicitly — and treat reconstructing the table from behaviour as a last resort, not a plan
R2 Windows refuses to load an unsigned KSP All testing blocks behind procurement, not just release Settle it in the first hour on the machine. Open the certificate purchase before you know the answer — it is the cheapest insurance in the plan
R3 Renewal with a new key fails (gate E, step E4) A CA that cannot be renewed is not a CA. Possible redesign Nothing more can be done blind: the refusal and the overwrite paths are both implemented and fault-injected. Which one ADCS exercises is an observation, so run E4 early
R4 The chosen HSM ships its own CNG provider This project may be the wrong tool for the job Ask the vendor before buying. An HSM with its own KSP does not need this one, and saying so now is cheaper than discovering it at the pilot
R5 The DACL risk is rejected The approach is ruled out, however well it works Get it in writing in week one. It is a governance question, and no amount of engineering changes the answer
R6 The first HLK run fails broadly Schedule, not architecture Expect it and budget for it. A suite's first execution tests the suite as much as the code — and a clean first run would be the more worrying result

Note what is not on this list: the cryptography, the threading, the PKCS#11 layer. Those have been run against two independent tokens, and five of the defects ever found there were caught the first time real hardware-like behaviour was involved. The residual risk is almost entirely in the layer Windows owns.

9 / 10

R1 and R2 are the ones to raise with whoever sponsors this. Both are procurement questions with engineering consequences, and both get worse the longer they go unasked. If R1 comes back negative the honest recommendation is to stop and buy an HSM that ships its own KSP — which is also R4, approached from the other side.

The first ninety days, and what “finalized” has to mean

Phrased against the header's arrival rather than a calendar, because the one thing that sets the schedule is the one thing nobody here controls.

First 30 days

Nothing depends on the DLL

  • Header escalation open; fallback decided
  • Certificate purchase under way
  • HSM qualified by p11_qualify; the authentication model known by measurement
  • DACL risk accepted or rejected, in writing
  • A4 closed; the Microsoft-documentation backlog retired
  • Pilot runbook written and reviewed by the CA operator

Days 30–60, from the machine's arrival

Gates B and C

  • The DLL builds; the signing question answered in the first hour
  • Registered; certutil lists it; the table layout confirmed
  • 190 tests executed and every failure classified
  • The DPAPI credential path proven, if the token needs a PIN
  • The CI Windows job compiles and links the real DLL

Days 60–90

Gate E, then the decision

  • E1–E7 twice on a throwaway CA, renewal included
  • Restart and reboot survived
  • Chains verified end to end, not merely API success
  • Test CA destroyed
  • A go or no-go recommendation with the evidence attached

Finalized means one sentence

A signed provider, on a certified HSM, running a certification authority that has issued, revoked and renewed — with the DACL limitation accepted in writing and the test CA destroyed. Anything short of renewal is not a finished CA; anything short of the signature is not a shippable provider.

Read every duration as relative: this project's effort estimates were wrong on 4 of the 4 rows it has ever closed · 10 / 10

Close on the one-sentence definition and leave it on screen. The three things most likely to be quietly dropped from a declaration of done are the signature, the renewal and the written risk acceptance — each is someone else's responsibility, which is exactly why each gets forgotten. Ask for the go or no-go recommendation as a deliverable, not as an opinion: a no-go with evidence at day 90 is a successful outcome for this plan.
