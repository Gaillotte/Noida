The question, and the honest answer

Can this provider hold a CA's private key? The architecture says yes. Nothing has ever loaded it.

What is proven

The PKCS#11 layer and every CNG entry point run against two real, independent tokens. RSA and ECDSA signing, key opening by name, certificate storage, 32-thread concurrency.

What is unproven

The DLL. It has never been compiled: ncrypt_provider.h declares the function table and is absent from the SDK, the WDK and mingw-w64 alike.

What is a decision

PKCS#11 has no ACL model, so a CA key cannot carry a Windows DACL. The token boundary is the whole control. That is a risk acceptance, not a patch.

The value of this provider is an HSM without a Windows KSP of its own — a token like Kryoptic, or a lab. An HSM that ships its own provider does not need this one.

Two layers, one translation each way

The KSP_ layer speaks CNG and knows nothing about Cryptoki. The P11_ layer speaks PKCS#11 and knows nothing about handles or blobs. Everything hard lives on the boundary.

Module Owns The design decision inside it
ksp_provider.c Open, Close, FreeBuffer, algorithm advertisement Advertises the intersection of what the KSP maps and what the token has — never a list compiled into the DLL
ksp_key_ops.c Create, Open, Finalize, Enum, Delete A taken container name is NTE_EXISTS; an overwrite destroys the old objects only after the new key generates
ksp_crypto.c SignHash, Verify, Encrypt, Decrypt, Export, Import, ECDH Size queries answer from the key, never by starting a token operation that would be left unfinished
ksp_properties.c Get and Set, key and provider scope Export policy is writable only before FinalizeKey — the token fixes CKA_SENSITIVE at generation
p11_context.c Module load, C_Initialize, slot choice A failed initialisation is retried; one bad module path must not poison the provider until the host restarts
p11_session.c 16 sessions, login, per-scope pools Scope is a mandatory parameter on acquire — a defaulted one would let a forgotten call site hit the wrong token and report success
p11_utils.c Mechanisms, DER, key export ECDSA signatures pass through raw r‖s as v2.40 §2.3.1 mandates; the DER decoder is a fallback only

Four contracts that shaped the code

Each of these was learned by breaking it

CNG calls everything twice

NULL buffer for the length, then again for the work. The first implementation answered the length by starting a token operation and returning without finishing it — the session went back into the pool live, and the next caller got CKR_OPERATION_ACTIVE. Lengths now come from the key.

The table is assigned by name

Designated initialisers against the SDK header, so a wrong slot name is a build error rather than a displaced function. Positional initialisation is permanently out — it once put a key handle where a HANDLE* belonged and returned success.

Every handle is a magic number

Handles are direct casts validated by dwMagic. All 26 slots are called with a bad handle in the suite, and completeness is enforced by comparing each probe against the real table slot by pointer — a new slot with no probe fails and names itself.

Misconfiguration fails closed

No PIN where one is required is NTE_PERM and a log line, never a silent attempt at 1234. Half-configured per-scope tokens, two labels resolving to one token, or a caller selection alongside them are all refused. Isolation that reports success without isolating is worse than none.

Memory is HeapAlloc on GetProcessHeap only; all 26 functions are re-entrant and tested as such · 5 / 15

The token decides how it is authenticated, not the provider

The provider reads CK_TOKEN_INFO.flags for the scope's slot and honours all three models PKCS#11 describes. Until recently it demanded a PIN of every token — so a hardware HSM with a PIN pad, the case this project targets, was rejected outright.

No login required

CKF_LOGIN_REQUIRED clear

No C_Login at all. No credential to store anywhere.

Protected path

PIN pad on the device

C_Login with pPin = NULL, per v2.40 §11.6. A configured PIN is deliberately not sent, only logged as unused. Ask your HSM vendor for this one.

PIN required

A credential must reach a headless service

certsrv never calls NCryptSetProperty, so the PIN has to be waiting for it. Four sources, in order.

Precedence

KSP_MACHINE_PIN / KSP_USER_PIN → NCRYPT_PIN_PROPERTY → DPAPI blob → SOFTHSM2_PIN

The blob outranks the ambient variable on purpose: a leftover lab variable must not silently downgrade a deployment that was provisioned properly, while appearing to work. And the registry ACL is the protection, not the encryption — machine-scope DPAPI can be unprotected by anything on the host.

A C_GetTokenInfo that fails falls through to the strict PIN model, and that direction is fault-injected · 6 / 15

Backend-agnostic by probe, not by porting

The provider always loaded whatever module a path pointed at — and then advertised a fixed list compiled into the DLL, describing one token. That was never a porting job; it was a correctness bug.

What the probe does

  • C_GetMechanismList once at initialisation
  • EnumAlgorithms answers the intersection of mapped and present
  • Generation and use are checked separately
  • A refused probe costs nothing — behaviour reverts to permissive
  • An implausible mechanism count abandons the probe rather than truncating it

What a probe cannot answer

Advertisement is not capability. SoftHSM2 advertises CKM_RSA_PKCS_OAEP and accepts only SHA-1, because the restriction lives inside the mechanism parameters. The probe is mechanism-granular; some limits are finer.

Strictness is not capability. Whether a token enforces CKA_WRAP is invisible to every query. So p11_qualify runs the requirements instead of reading them.

Test strategy

Five layers, and only two of them have ever run

Layer 4

Microsoft HLK, in HLK Studio

Controller plus a separate test client. Never executed.

Layer 3

PowerShell, 9 scenarios + ~150 HLK checks

NCrypt by P/Invoke, verified against BCrypt. Syntax-checked on Linux; never executed.

Layer 2

40 integration tests, Windows + live token

Written and parse-checked. Never executed — a suite that has never run is a hypothesis about the suite.

Layer 1b

The real sources against a real second token

Kryoptic, unrelated to this repository. Only the loader is substituted. Runs in CI.

Layer 1

27 unit suites, 2 051 assertions

Linux/GCC against a PKCS#11 mock. 86.2 % lines, 100 % functions. Runs in CI.

The pyramid is upside down where it matters: everything that needs Windows is unexecuted, so layer 1b was built to move as much risk as possible below that line.

The discipline

A green test proves nothing until you have watched it go red

Every claim in this project is established by breaking the code and confirming the suite catches it. The habit exists because vacuous tests kept passing: one asserted a defect as the expected behaviour, another compared two handles that could be swapped freely.

Five defects the mock could not see

  • ECDSA signing had never worked against a conformant token — the provider decoded DER where v2.40 mandates raw r‖s, and the mock returned whatever DER the test had just built
  • A size query poisoned the session pool
  • A deleted key left its certificate on the token
  • HMAC and CMAC signing had never worked
  • A key opened by name lost its modulus size, so every signature failed at CNG's first call

And three traps in the harness itself

  • Building one test binary silently rebuilt nothing, so four consecutive fault injections ran against a stale binary and looked undetected — the worst possible failure for the one tool whose job is to show a test can fail
  • Ten stubs were never checked against the real prototype, so a signature change produced ten segfaults and no diagnostic
  • A grep for a fix matched the comment describing the fix, and reported ten files as correct when none was

Restore an injection from a copy, never from git — that mistake has cost uncommitted work three times · 10 / 15

Five static checks, because prose does not stay true

The project's most persistent defect is not a bug. It is a summary of a fact, sitting next to the fact, not updated with it — found in the feature matrix, the property tables, the test counts, the registration script and the vendor-facing requirements document. Each one became a machine-checked invariant instead.

check_mock_drift.py

The test mock against the real Windows headers — values and typedef widths. The mock once invented two constants and mis-valued two more, and every test passed because the tests read the same wrong numbers.

check_registration.py

The registration script against what the provider advertises, both ways. Found AES-CMAC advertised and never registered, and RSA decryption implemented and undiscoverable — never published under the asymmetric-encryption interface.

check_property_docs.py

The property tables against the dispatch chains, in both directions and including the read and write columns. Its first run reported four real defects — one documented property did not exist at all.

check_test_counts.py

Every documented suite and assertion figure against the suite's own run log. The historical session entries are deliberately excluded — a check that flags the record as drift pressures the next reader into falsifying history.

check_generated_artifacts.py

Four generated documents against their inputs, by fingerprint. It compares inputs rather than outputs, because every artifact embeds a date and two are binaries with unstable internal ordering.

The weakest gate was the one nobody could run

The mingw cross-compile is the only check that compiles Windows-only code, and it did not promote an implicit declaration to an error where the unit build did. It let a truncated Win64 heap pointer through with exit 0.

All five run in the Linux CI job and need no toolchain · 11 / 15

Installation · step 1 of 3

Build the DLL — and find the header first

Prerequisites

  • Windows 10/11 x64, elevated prompt
  • Visual Studio with the x64 toolset, and CMake
  • ncrypt_provider.h — associated with the Cryptographic Provider Development Kit; absent from the SDK, a WDK install and mingw-w64
  • A PKCS#11 module: SoftHSM2 for the lab, the vendor's library for production
  • An OV or EV code-signing certificate, bought by a verified legal entity

Commands

git submodule update --init --recursive
.\softhsm_ksp\tools\build_softhsm_windows.ps1

cd softhsm_ksp; mkdir build; cd build
cmake .. -A x64 `
 -DSOFTHSM2_DIR=..\..\softhsm2-install `
 -DCPDK_INCLUDE_DIR=C:\cpdk\include
cmake --build . --config Release

..\tools\sign_ksp.ps1

Omit the header and CMake skips the DLL

Deliberately — a provider with no entry point is worse than no provider. The build warns instead, and the other nine files still compile.

Settle signing in the first hour

Whether ncrypt.dll refuses to load an unsigned user-mode KSP is unconfirmed. If it does, that is a procurement lead time, not a code change.

Don't pin a Visual Studio generator: runners move past it. Let CMake pick · 12 / 15

Installation · step 2 of 3

Register the provider, then give it a token and a credential

Commands, elevated

.\register_ksp.ps1 -DllPath C:\KSP\softhsm_ksp.dll
certutil -csplist

setx /M KSP_PKCS11_LIB "C:\hsm\vendor-p11.dll"
setx /M KSP_MACHINE_TOKEN_LABEL "CA-MACHINE"
setx /M KSP_USER_TOKEN_LABEL  "CA-USER"

.\set_ksp_pin.ps1 -Scope Machine `
 -ServiceAccount 'NT Service\CertSvc'

setx /M KSP_DEBUG 1  # DebugView, pilot only

Registration is two things, not one

The binary goes in with BCryptRegisterProvider; the algorithm list goes in with BCryptAddContextFunctionProvider. Writing the registry values by hand does only the first: the provider loads, reports no algorithms, and anything discovering providers by algorithm skips it.

Two tokens, not two label prefixes

Set the pair and NCRYPT_MACHINE_KEY_FLAG selects which token — own PIN, own session pool. Without them the scopes are a label prefix inside one token, which is namespacing, not isolation. Half-configured is refused.

Then restart anything already running. CNG reads the provider list at process start, so certsrv will not see a newly registered provider until it restarts. And remove SOFTHSM2_PIN once the blob is provisioned, or you cannot tell which credential a successful login used.

set_ksp_pin.ps1 reads the PIN with Read-Host -AsSecureString, so it never reaches the process list or the shell history · 13 / 15

The backlog is no longer about code

One header, one Windows machine, three decisions and your HSM. Of the open capability rows in the feature matrix, 10 of 30 can start here; the rest are blocked outside this repository.

Phase What is left What it is blocked on
BBuild the DLL; register it; run the 40 integration tests and ~150 conformance checks for the first time; confirm the table layoutncrypt_provider.h and a Windows machine. This is the critical path, and it has no engineering content

—16 entry points answer NTE_INVALID_PARAMETER for a bad handle where 7 answer NTE_INVALID_HANDLEMicrosoft's documented mapping, unreachable from this workspace. Deliberately unchanged rather than altered on a recalled contract

Decide: target token

If the HSM ships its own KSP, this project may not be the right tool at all.

Ask the vendor for C-c

A protected authentication path removes the credential from Windows entirely, and is already supported.

Read the sizes as relative

This project's effort estimates were wrong on 4 of the 4 rows it has ever closed. Two were marked "no remedy planned" and closed in a day.

Either the vendor's PKCS#11 library or a Windows machine with the CPDK unblocks more than anything else · 15 / 15
